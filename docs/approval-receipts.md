# Approval receipts

An approval receipt is a short-lived, signed statement that MoorAI allowed, or a person approved, one exact MCP
tool call. MoorAI attaches it to the call's arguments as `_moorai: { "receipt": "<wire>" }`. An MCP server that
holds privileged tools, such as a remote-administration hub with its own approval queue, verifies the receipt and
skips its queue only for a receipt it can verify from a trusted source. Every other call is queued as before.

Code: [`cli/approval-receipts.mjs`](../cli/approval-receipts.mjs) (payload, signature, wire form, reference
verifier), [`cli/canonical-json.mjs`](../cli/canonical-json.mjs) (the canonical JSON writer),
[`cli/receipt-step.mjs`](../cli/receipt-step.mjs) (the hook's side), [`cli/approval-routing.mjs`](../cli/approval-routing.mjs)
(console receipts on approvals). Tests: `test/approval-receipts.test.mjs`, `test/approval-receipts-hook.test.mjs`.
Test vectors: [`test/fixtures/approval-receipts/vectors.json`](../test/fixtures/approval-receipts/vectors.json),
regenerated by `node scripts/gen-receipt-vectors.mjs`.

## 1. Payload

A JSON object with exactly these fields (no others):

| Field | Type | Value |
|---|---|---|
| `v` | integer | `1` |
| `typ` | string | `"moorai.receipt"` |
| `aud` | string | the hub's audience id, from the signed policy's `approvalReceipts.audiences[].aud` |
| `tool` | string | the MCP tool name as the server sees it: the bare name, with Claude Code's `mcp__<server>__` prefix stripped (`run_command`, never `mcp__it-ai__run_command`) |
| `argsSha256` | string | lowercase hex SHA-256 of the canonical JSON (§2) of the parsed tool arguments with the top-level `_moorai` key removed |
| `device` | string | the device's keyed actor pseudonym (`h2:` + 16 hex: the tenant-keyed hash of user@host that every alert already carries as `actor`); never a hostname or login |
| `session` | string | the keyed session hash already sent on alerts as `session` (`h2:` + 16 hex), or `""` when the host gave no session id |
| `nonce` | string | 32 lowercase hex characters, random |
| `iat` | integer | issue time, Unix seconds |
| `exp` | integer | expiry, Unix seconds; `exp - iat` is 1 to 120 |
| `basis` | string | `"approved"` (a person approved it) or `"allowed"` (MoorAI's policy allowed it) |
| `approvalId` | string | the approval request id (`apr_` + 26 Crockford base32 characters); present only with basis `approved` |
| `approver` | string | optional; a keyed pseudonym of the approver, set only on console receipts; never a name or email |
| `keyId` | string | the signing key's id (§3) |
| `keySource` | string | `"console"`, `"helper"` or `"device"` |

Rules: basis `approved` requires keySource `console` and an `approvalId`; `approvalId` appears only with basis
`approved`; `approver` appears only with keySource `console`; a device receipt is always basis `allowed`.

Content-free: a receipt carries a hash of the arguments, never the arguments.

## 2. Canonical JSON

One writer, [`cli/canonical-json.mjs`](../cli/canonical-json.mjs), also used for the signed policy digest and the
approval actionHash:

- Object keys sorted recursively, in JavaScript's default sort order (UTF-16 code units). For ASCII keys this is
  byte order. A hub whose map sorts by UTF-8 bytes agrees on every key that has no character above U+FFFF mixed
  with characters in U+E000..U+FFFF.
- No insignificant whitespace: `,` and `:` with nothing around them. Output is UTF-8.
- Strings as ECMAScript `JSON.stringify` writes them: `"` and `\` escaped; `\b \f \n \r \t` in short form; other
  control characters below U+0020 as `\u00xx` with lowercase hex; `/`, DEL and non-ASCII characters written
  as-is (UTF-8); a lone surrogate as `\udxxx`.
- `true`, `false`, `null` literally.
- **Numbers** as ECMAScript `Number::toString` writes them (what `JSON.stringify` does): an integer as its digits
  with no fraction or exponent (`30`, `-7`); `-0` as `0`; a non-integer in the shortest form that round-trips
  (`0.1`, `2.5`); a magnitude of 1e21 or more, or below 1e-6, in exponent form (`1e+21`, `1e-7`). A JSON number
  is an IEEE-754 double when Claude Code and MoorAI parse it, so an integer above 2^53 has already been rounded
  to the nearest double before it is hashed (`9007199254740993` arrives as `9007199254740992`).
- **The hub's number rule.** A hub verifier need not reproduce float formatting. A hub queues any call whose
  parsed arguments contain a number that is not an integer within ±(2^53 − 1) ("hub queues: non-integer
  number"), even when the receipt verifies. The vectors `non-integer-float` and `integer-above-2-53` show both.
- `argsSha256` is computed over the canonical JSON of the PARSED arguments, never over the bytes that were
  received. The vector `console-approved-int-bool-approver` arrives with its keys in a non-canonical order.

## 3. Signature, wire form and keys

- **Signed bytes:** the UTF-8 bytes of `"moorai-receipt|v1|" + canonicalJson(payload)`.
- **Signature:** ed25519 (RFC 8032), 64 bytes.
- **Wire form:** `base64url(canonicalJson(payload)) + "." + base64url(signature)`, base64url without padding. The
  payload part is the canonical JSON itself; a verifier re-serializes the decoded payload and refuses it when the
  bytes differ.
- **On the call:** the tool arguments gain a top-level key `"_moorai": { "receipt": "<wire>" }`.
- **Public key encoding:** the raw 32-byte ed25519 public key as base64url without padding (43 characters).
- **keyId:** the first 32 lowercase hex characters of SHA-256 over the raw 32-byte public key. This is the key-id
  convention of the console's policy-signing key and of the device key
  ([`cli/guardd-client.mjs`](../cli/guardd-client.mjs) `keyIdOfSpki`).

### Key sources

| keySource | Who signs | basis | Hub |
|---|---|---|---|
| `console` | the console, when a person approves a just-in-time approval | `approved` | skips its queue (basis `approved` with an `approvalId` only) |
| `helper` | reserved for the privileged local helper (`moorai-guardd`) once it is installed; this agent does not sign with it | `allowed` (basis `approved` is console-only) | skips its queue |
| `device` | the hook, at call time, with the device's existing ed25519 key (`~/.moorai/agency-ed25519.key`, the key of the signed MCP decision tokens and decision receipts) | `allowed` only | queues |

A device receipt is **advisory**. The device key lives in the agent user's home directory, so any process
running as that OS user can read it and sign a receipt for any call. A hub must never let a device receipt skip
its queue.

## 4. Delivery (the hook)

### Policy field

```
approvalReceipts: { v: 1, audiences: [ { aud: "<id>", mcpServer: "<server name, e.g. it-ai>", tools?: ["<tool glob>"] } ], ttlSec: 60 }
```

- Read from the verified policy only (the same copy that decides the hook's fail mode; on a device with no anchor
  and no pin that copy is the user-scope policy, which only affects device receipts, which are advisory).
- `aud`: 1 to 128 characters of `A-Z a-z 0-9 . _ : / -`. `mcpServer`: the server segment of the Claude Code tool
  name (`mcp__<server>__<tool>`), matched exactly; a plugin-bundled server's segment is
  `plugin_<plugin>_<server>`. `tools`: optional; bare tool names (the console writes exact names; this agent also
  reads `*` as any run of characters), anchored. With no `tools`, every tool of the server is covered. Either way
  `click`, `type_text`, `press_key`, `upload_file`, `download_file` and `push_file` never get a receipt (the
  console refuses them in a list too). At most 16 audiences and 64 entries each; a malformed audience is dropped
  with a stderr warning that names its index.
- `ttlSec`: the lifetime of the receipts this device signs; 60 when absent, capped at 120.
- With no `approvalReceipts` field, or none valid, nothing changes.
- `aud` must equal the hub's own configured audience (`MOORAI_RECEIPT_AUD`, §6); the policy does not set it at the hub.

Example for a remote-administration hub, with the 19 tools that hub binds receipts to
(`HUB_RECEIPT_TOOLS` in [`cli/approval-receipts.mjs`](../cli/approval-receipts.mjs)):

<!-- example-approvalReceipts -->
```json
{ "approvalReceipts": { "v": 1, "ttlSec": 60, "audiences": [ { "aud": "it-ai-hub-1", "mcpServer": "it-ai",
  "tools": ["run_command", "job_start", "job_stop", "update_agent", "dissolve_agent", "device_action", "message_user",
            "install_package", "uninstall_package", "run_plugin", "system_report", "check_updates", "compliance_posture",
            "run_script", "fleet_run", "fleet_report", "run_script_fleet", "screenshot", "camera_snapshot"] } ] } }
```

Never list `click`, `type_text`, `press_key`, `upload_file`, `download_file` or `push_file` (`HUB_EXCLUDED_TOOLS`):
the hub never accepts a receipt for them. Receipts are single-use per hub request; an input event is one request
per keystroke or click (and `click`'s float coordinates fail the hub's number rule, §2), and a receipt cannot cover
`push_file`'s staged file bytes, so those always queue.

### What the hub binds per tool

The receipt binds the tool name and the argument hash; the hub also checks the action kind inside the arguments
against the tool, with no change to the payload format. It refuses a receipt when:

- `system_report` or `fleet_report` carries a kind that is not a report kind (a `system_report` receipt with
  `kind=reboot` is refused);
- `device_action` carries a kind that is not a device action;
- `run_plugin` carries a kind other than the plugin kind;
- `check_updates` or `compliance_posture` carries a kind other than its own;
- `run_script` selects the script by guid rather than by file name.

A refused receipt leaves the call queued. A console approval screen or a hook message that shows the tool name must
not suggest such a combination will skip the hub's queue.

`run_command` on a device the hub reaches directly on the LAN can consume the receipt when the hub mints its
capability for that device. If the call then falls back to the relay, the relay request is queued for approval
again.

### Which calls, and the answer

For a Claude Code `PreToolUse` MCP call (`mcp__<server>__<tool>`) under a policy with `approvalReceipts`:

1. A top-level `_moorai` key in the input is removed before any check runs. The checks, the approval actionHash and
   `argsSha256` see the input without it, and the input that goes on is the stripped one. A model or a poisoned
   tool result cannot smuggle a receipt through.
2. When the final verdict is **allow** and the call's server (and tool, when globs are set) is listed, the hook
   answers `hookSpecificOutput.updatedInput` = the full input plus `_moorai: { receipt }`, with no
   `permissionDecision`, so Claude Code's own permission flow still runs. The receipt is the console's when an
   approval's first use allowed the call (§5); otherwise it is signed with the device key (basis `allowed`).
3. A call the hook **asks** on carries no receipt. When its input had `_moorai`, the stripped input goes with the
   ask. A **denied** call carries nothing.
4. A call to a server or tool that is not listed gets no receipt; a `_moorai` key in its input is still removed.
5. On a host that cannot rewrite input, a call whose input carries `_moorai` is **denied** (reason code
   `RECEIPT_KEY_INJECTED`), because the key cannot be removed. Without the key the call is judged as usual and
   gets no receipt.

The receipt is minted on the final verdict, after approval routing, capability tags, session-risk escalation,
server-mode and bypass-mode settling and the fail mode. A verdict that ends as ask or deny never carries one.

### The `updatedInput` contract

Claude Code's hooks reference (code.claude.com/docs/en/hooks, PreToolUse decision control) says `updatedInput`
"Replaces the entire input object, so include unchanged fields alongside modified ones." The hook therefore sends
the complete input (every original field, after any mask) plus `_moorai`.

Measured, Claude Code 2.1.295, `claude -p` with a local stdio MCP server that logs the arguments it receives and a
`PreToolUse` hook that answers `updatedInput` = input + `_moorai: { receipt: "PROBE.SIG" }` and no
`permissionDecision`. One tool declared `{ msg: string }`, the other the same with `additionalProperties: false`.
The server logged:

```
{"name":"echo_args","arguments":{"msg":"hello","_moorai":{"receipt":"PROBE.SIG"}}}
{"name":"strict_echo","arguments":{"msg":"hello","_moorai":{"receipt":"PROBE.SIG"}}}
```

Claude Code applied `updatedInput` to MCP tools and did not validate the extra key away, even against a schema
with `additionalProperties: false`. The hook's input carried `mcp_server: {"name":"probe","source":"dynamic"}`.
An MCP server whose own argument parsing rejects unknown fields would refuse the call. A server that echoes its
arguments puts the receipt into the model's context, where it is single-use and expires within 120 s.

### Hosts

| Host | Receipt | `_moorai` in the input |
|---|---|---|
| Claude Code (CLI, IDE extensions, desktop, server mode) | attached on an allowed listed call | stripped (allow, ask) |
| Cursor CLI running these hooks (`CURSOR_VERSION` set) | none: whether it honours `updatedInput` is unmeasured | call denied |
| Codex, Copilot CLI, Gemini CLI, Windsurf, Kiro, Cline, Droid, Antigravity (the adapters in `cli/agent-hooks/`, `MOORAI_HOOK_HOST=shim`) | none: the shim reduces the answer to allow / ask / deny and drops `updatedInput` | call denied |
| A tool name that arrived under an alias | none | call denied |
| An unenrolled (coached) device | none | unchanged (a coached device changes nothing) |
| `moorai-guard`, the MCP gateway, the model proxy | none: they do not mint receipts | unchanged |

## 5. Console receipts and approvals

When an MCP call covered by `approvalReceipts` is held for approval
([APPROVAL_ROUTING.md](APPROVAL_ROUTING.md)), the `APPROVAL_REQUESTED` alert's `approval` object gains two fields:

```
approval.receiptArgsDigest: "h2:<16 hex>"                                   contentHash(argsSha256), safe to store
approval.receiptRequest:    { "aud": "...", "tool": "<bare tool name>", "argsSha256": "<64 hex>" }
```

- `receiptArgsDigest` is the tenant-keyed digest of `argsSha256`. It belongs to the alert body and may be stored and
  sent to SIEM like `contentHash`.
- `receiptRequest` carries the raw, unkeyed `argsSha256`, which can be guessed for arguments from a small value
  space. The console uses it only to mint the receipt and **must strip it before alert storage, before SIEM
  forwarding and before any export** (keeping `aud` and `tool`). It is never on any other alert. The alert chain
  covers `receiptRequest.aud` and `receiptRequest.tool` but not `receiptRequest.argsSha256`
  ([`cli/alert-seq.mjs`](../cli/alert-seq.mjs) `alertChainView`): `seq` / `chainHead` are computed over the alert
  with only that one field removed, so the stored alert, stripped of the raw hash, still checks against its link,
  and a changed `aud` or `tool` does not. The raw hash is bound through the chained `receiptArgsDigest` and
  `actionHash` (below). The outbox's `rhash` is computed the same way.
- The local alert outbox (`~/.moorai`) may hold the request until it is delivered. That discloses nothing new: the
  device already holds the arguments themselves.
- The console takes the receipt's `device` from the alert's `actor` and its `session` from the alert's `session`,
  the same values a device receipt carries.
- The receipt itself still carries the raw `argsSha256`. It goes only to the device, which has the arguments, and
  to the hub, which receives them with the call; a hub must hash the arguments to verify the receipt at all.

The request's `actionHash` for such a call is bound to the same `{ argsSha256, aud, tool }`, so the console can
check that the request and the receipt agree before it mints, and an audience changed in transit changes the hash:

```
actionHash = contentHash("approval" + U+0000 + canonicalJson({ "argsSha256": <argsSha256>, "aud": <aud>, "tool": <bare tool name> }))
contentHash(s) = "h2:" + first 16 lowercase hex of HMAC-SHA256(K, UTF-8 s)
K              = HMAC-SHA256(key = <tenant installToken>, data = "moorai/content-hash/v2")
```

For example `approval\u0000{"argsSha256":"<64 hex>","aud":"it-ai-hub-1","tool":"run_command"}`. Each vector
carries `actionHashInput` (with the receipt's `aud`) and the `actionHash` under the test install token. The server
name is not in the hash: two listed servers that share one `aud` and a bare tool name share an actionHash for
identical arguments, so give each server its own `aud`, and give receipt-bound rules an `mcpTool` match. Calls not covered by `approvalReceipts` keep the earlier
actionHash over the tool name and the key-sorted input.

When a person approves, the console mints a receipt (keySource `console`, basis `approved`, `approvalId` = the
request id, optional `approver`) and returns it in the signed policy's `approvals` row as `receipt` (the wire
string). The device reads it only from a policy whose signature verifies (as every grant), and attaches it
**unchanged** when the approved identical call runs. One approval runs exactly one action:

- The console mints at most one receipt per approval request (its `approval_receipts` table is keyed on tenant and
  request id; a second mint returns the stored receipt).
- The device attaches it only on the grant's first use (`decideHeld` in
  [`cli/approval-routing.mjs`](../cli/approval-routing.mjs) returns the receipt only when the request id is not yet
  recorded as used in `~/.moorai/approvals.json`). That file is in the agent user's write scope, so a device can be
  made to present the same receipt again; the hub refuses it.
- At the hub the `nonce` and the `approvalId` are **each** single-use: a receipt whose nonce was seen, or whose
  approvalId was seen with any nonce, is refused.

A later use of a `ttl` grant, or an approval with no console receipt, gets a device receipt (basis `allowed`), which
the hub queues.

**Delivery: live once `moorai-guardd` is installed and bound.** The console puts `approvals[].receipt` in
`/api/policy` only when all of these hold:
- the fetch is signed by the device's BOUND helper key. That is the `moorai-guardd` device key, registered with a
  one-time enrolment secret, and the console checks it with `verifySignedRequest` over method, path and query;
- that key's device is the request's device;
- the install token is the one that posted the request.

The helper makes that fetch:
- `GET /api/policy?tenant=<t>&actor=<the hook's keyed actor>`, the hook's own query;
- signed in the contract §6.2 form, `moorai-devreq|v1|GET|<path and query as sent>|<tenant>|<deviceId>|<keyId>|<ts>|<nonce>|<sha256 of the empty body>`;
- with `X-Device-Id`, `X-Device-Key`, `X-Device-Ts`, `X-Device-Nonce` and `X-Device-Sig` beside `X-Install-Token`.

The hook reads the policy through the helper's socket (`cli/guardd-policy.mjs`; contract §3.4 `policy`, with the
hook's `actor`):
- the helper answers from what it holds when it fetched for that actor within the last 60 s;
- otherwise it fetches on demand, bounded to 1 s, and the hook waits at most 1.3 s;
- the hook verifies the helper's policy like a fresh fetch: signature, tenant and rollback mark.

The hook falls back to its own install-token fetch, which carries no receipt, when:
- no helper is installed;
- the helper does not answer, or fails its device-key proof;
- the helper serves another tenant, or holds no fresh policy;
- the hook's actor is not the one the helper derives for its OS user (§8);
- the policy does not verify.

The device then goes on with a device receipt (basis `allowed`), and the hub queues the call. The same happens
when the helper registered unbound (no enrolment secret): the console serves the policy but withholds the receipt.

The only key the hook itself holds is the device receipt key in `~/.moorai`, which any process of the agent's OS
user can read. It is never used to sign the policy fetch.

Install it (macOS) with `sudo sh guardd/packaging/macos/install.sh <binary> --bind --server-url <console> --tenant <tenant> --enroll-secret-file <file>`
(README, "Privileged helper"). Then `sudo sh guardd/packaging/macos/install.sh --check` reports
`ok registered and bound`. Linux and Windows have no helper platform layer yet, so on those systems receipts stay
dormant. Tested:
- `test/guardd-policy-e2e.test.mjs`: the real helper binary, a test console that decides with the console's
  `receiptAuthFor` and `verifySignedRequest` copied verbatim (`test/fixtures/guardd/console-verifier.mjs`), and the
  hook's loader. The receipt arrives through the helper and not on the direct fetch;
- `test/guardd-policy.test.mjs`: the fallbacks;
- `guardd/tests/helper_e2e.rs` and `test/guardd-actor-parity.test.mjs`: the helper derives the peer's actor as the
  hook does (shared vectors `guardd/tests/fixtures/actor-vectors.json`) and refuses any other actor;
- `test/approval-receipts-hook.test.mjs` ("approval without a console receipt"): the device-receipt path.

A console receipt expires at most 120 s after the console mints it. An approval that reaches the device later
than that carries an expired receipt, and the hub queues the call.

## 6. Hub verification

The hub pins its keys and its audience from its own configuration and does not fetch `/api/policy/pubkey`:

- `MOORAI_RECEIPT_AUD`: the hub's audience id. The policy's `audiences[].aud` must equal it.
- `MOORAI_RECEIPT_KEYS`: `[{ "keyId", "publicKey", "keySource" }]`, `publicKey` the raw 32-byte key as base64url
  without padding, `keySource` the source the key was pinned for. **Trust follows the pinned key's keySource, never
  the payload's.** A payload whose `keySource` differs from its key's is refused.

Steps, in order (the reference verifier `verifyReceipt` in [`cli/approval-receipts.mjs`](../cli/approval-receipts.mjs)
returns these reason codes):

1. Take `_moorai.receipt` from the arguments. Two base64url parts separated by one `.`, no padding (`malformed`).
2. Decode the payload; it must be a JSON object whose canonical JSON equals the decoded bytes (`not_canonical`), with
   no field outside §1 (`unknown_field`), `v` 1 and `typ` `moorai.receipt` (`bad_version`).
3. Look up `keyId` in the pinned keys (`unknown_key`).
4. Verify the 64-byte ed25519 signature over `"moorai-receipt|v1|"` + the decoded payload bytes (`bad_signature`).
5. `aud` equals `MOORAI_RECEIPT_AUD` (`wrong_aud`).
6. `tool` equals the called tool's name (`wrong_tool`).
7. Remove `_moorai` from the parsed arguments; `argsSha256` equals SHA-256 of their canonical JSON (`args_mismatch`).
8. `iat` and `exp` integers with `exp > iat` (`bad_time`), `exp - iat ≤ 120` (`ttl_too_long`),
   `iat ≤ now + 30` (`not_yet_valid`), `now < exp` (`expired`). `nonce` is 32 hex (`malformed`).
9. `keySource` and `basis` from the allowed sets, the payload's `keySource` equal to the pinned key's, and the §1
   rules between basis, `approvalId`, `approver` and keySource (`bad_basis`).
10. Replay: the nonce and the approvalId are each single-use. Refuse a receipt whose `nonce` was seen, or whose
    non-empty `approvalId` was seen (with any nonce) (`replay`); record both.

**Trust rule.** The hub skips its queue only for a receipt that passes every step AND whose pinned key is
`console` with basis `approved` and an `approvalId`, or whose pinned key is `helper`, AND whose arguments contain
only integers within ±(2^53 − 1). Everything else is queued: a device receipt, a console receipt with basis
`allowed`, an invalid receipt, no receipt.

The hub treats `keyId` as an opaque string matched against its pinned keys. It labels a valid device receipt
"advisory: MoorAI device receipt" and queues the call.

## 8. Limits

- A device receipt proves nothing a same-user process could not forge; only console (and, once installed, helper)
  receipts carry trust.
- `argsSha256` is an unkeyed SHA-256, so arguments from a small value space can be guessed from it by whoever holds
  the receipt (the hub, and the model if the server echoes it).
- A mask that rewrites a call's arguments after a console receipt was minted for the unmasked call makes the
  hashes differ, and the hub queues the call.
- If the hook crashes or times out (and the fail mode is open), it answers nothing and the call goes on as the
  model wrote it, `_moorai` included.
- Claude Code alone is measured to deliver `updatedInput` to MCP tools (§4).
- Console receipts reach the hook only through an installed and bound `moorai-guardd` (§5), today on macOS only.
  The console binds a receipt to the device, not to the OS user. The helper enforces the per-user split itself:
  - it keys every actor's policy by actor, in memory only, and answers a request only from that actor's own entry;
  - its background fetch names no actor, and its cache and last-known-good never hold an actor's policy;
  - it derives each request's actor from the peer and never takes it from the message: the IPC peer's uid (from
    the kernel, `LOCAL_PEERCRED` / `SO_PEERCRED`) resolved to its login name (`getpwuid_r`), the helper's own
    install token (root-owned `secret.json`) and the hostname, hashed exactly as the hook's `actorHash`
    (`guardd/src/policy.rs` `derive_actor`, pinned to `cli/content-hash.mjs` by
    `guardd/tests/fixtures/actor-vectors.json`);
  - a request naming any other actor gets `source: "none"` and fetches nothing, so a local user who can compute
    another user's keyed actor gains nothing by claiming it, before or after a helper restart;
  - a request naming no actor is served the derived one; when no actor can be derived (no install token, or
    the uid has no login name), only the actor-less policy is served, never an actor's;
  - the derived actor is bound to its uid: one actor per uid, in memory.

  What remains: the hook gets its receipts through the helper only when its own actor equals the derived one,
  so the hook's install token must be the helper's and the hook must name the user and host the kernel reports.
  A hook in server mode (a service identity, `svc:<id>`) or with another install token gets `source: "none"`
  and takes its direct path with no receipt. Two uids with the same login name derive the same actor; the one
  that asks first holds it and the other gets `source: "none"`.
